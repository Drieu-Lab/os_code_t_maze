# Bugs

Quick capture of things that are broken or wrong. One bullet each; rough is fine.
See [`README.md`](README.md) for how these get triaged.

Format: `- #YYMMDD_ShortName <what's wrong> [where, if known]`

Assign a unique `#YYMMDD_ShortName` handle once, date-first (e.g.
`#260710_DoubleReward`). The date prefix is the creation date, so no separate
date column is needed. Don't rename a handle after you've referenced it elsewhere
(commits, `future-work.md`) so those references stay valid.

- #260727_SerialLockout The Due stops talking to the host mid-run while staying enumerated in Device Manager (no error code, nothing in the Windows event log). Manual feed / speaker buttons do nothing, the GUI readouts just stop updating, and restarting the rig fails with `PermissionError(13, 'A device attached to the system is not functioning.', None, 31)`. The Due's RESET button recovers it (no cable replug needed), which points at a hung firmware `loop()` - the SAM3X services its USB CDC endpoints from `loop()`. Twice on 2026-07-27: (1) 29 s into a Phase 3 session with H.264 recording, last line `S,3,1` at 13:43:46 (firmware uptime 16.2 min); (2) on a completely idle board - empty maze, nothing recording, no tones since boot - dead somewhere in the 19-minute window between 14:06:17 and 14:25:35. Correlates with the PROTO v6 reflash (`254c6c5`, 2026-07-23), and Phase 2a on pre-v6 firmware ran 30-60 min repeatedly without it, but the idle case may be an older mode nobody had watched for. Ruled out: pins 4/5 (unwired), USB contention with the camera (it is GigE), host CPU/disk load, USB bus events, dead USB hardware. **Partly addressed:** the host now detects it in ~25 s and logs it instead of silently freezing for 17 minutes (ADR-0062), and the always-on 80 kHz tone interrupt - the leading suspect for the idle case - now runs only while a tone sounds (ADR-0063). Root cause still unconfirmed; keep open until an idle board survives 30+ min on the reflashed firmware. Remaining suspects: the `CONFIRM wired` TONE_ON/TONE_OFF TTL pins 6/7, a latent out-of-bounds write, or a non-firmware change from the same week (an `FTDI FT600 USB 3.0 Bridge Device` shares the Due's USB controller).
  - [update 2026-07-27] Both fixes are live: the broker changes are in, and the gated tone timer is flashed and bench-verified (4 kHz + 8 kHz clean, Phase 3 cue fires).
  - [occurrence 3, 2026-07-27, on the reflashed firmware] **Wedged again, so the always-on tone interrupt is NOT the cause** (ADR-0063's suspect is excluded). Port opened 15:53:12; the rig then sat idle, with the liveness probe exchanging a `STATUS` and a reply every ~10 s (`from_due=1 to_due=0 probes=1`, unbroken for 16 minutes); the probe's write failed at **16:10:23** (~17 min of connected time) and every reopen failed with error 31. Two new things ruled out: it is **not** specific to a fully silent link (the host talked every 10 s and the board answered every time, so its `loop()` was alive to the end - the hang is abrupt, not gradual), and it is not tone-related (no tone since ~15:54). Detection took **~13 s** instead of 17.5 min, which is the whole point of ADR-0062. New lead: occurrence 1's last line was firmware uptime 972401 ms (16.2 min) with death inside the next 88 s, and occurrence 3 died at ~17 min - two deaths in a **16-18 min band**, suggesting a TIME-triggered failure rather than an activity-triggered one (2^20 ms = 17.48 min is the nearest suspicious boundary). To confirm, read the firmware `ms` on the last line of this run's `rig_logger` CSV. Next experiment, now cheap because death is timestamped: flash pre-v6 (`254c6c5^`) and repeat the same idle soak - survives 30+ min means the bug is inside the v6 diff, dies at ~17 min means v6 is exonerated.
  - [occurrence 4, 2026-07-27, idle soak with the camera held by Pylon Viewer] Same failure, and **the timing is now the strongest clue we have**. Port opened 16:19:58, probe write failed 16:37:13: **17 min 15 s**, against occurrence 3's 17 min 11 s (15:53:12 -> 16:10:23). Two runs landing 4 s apart rules out a load- or data-dependent cause, and this run also clears the GUI's camera (Pylon Viewer held it, so the host app never touched the camera) - an open CDC port with a `STATUS` every 10 s is the entire workload needed to trigger it. Occurrence 1 anchors the same clock in *firmware uptime*: the board booted at 13:27:34 on the replug and its last line read uptime 972,401 ms, which lands at 13:43:46.4 against the logged 13:43:46.774, so the firmware clock was true and death fell between uptime 972 s and 1,060 s (first failed write 13:45:14). Runs 3 and 4 only give lower bounds on uptime (the board booted at or before the port opened), but intersecting all three puts every death at **uptime 1,035-1,060 s**, with 2^20 ms = 1,048.576 s sitting inside that band. Caveat before believing "time": the two idle runs also exchanged the same *number* of messages (~101 probes at 10 s), so elapsed time and message count are perfectly confounded.
    - **E1 (breaks the confound, no code change now that the schedule is a flag):** `python rig_broker.py --port COM4 --probe-quiet 2 --probe-interval 2 --probe-dead 8` and leave it idle. Dying at ~17 min again means it is time; dying at ~3.5 min (~101 probes) means it is message count. **Done - see occurrence 5.**

  - [occurrence 5, 2026-07-28, E1 - idle soak probing every 2 s] **Message count is excluded: the trigger is a clock.** ~515 exchanges instead of ~103, all answered 1:1, and it still died 17 min 10 s after the port opened (RESET pressed with the broker running at ~12:13:55, `serial open` 12:13:58, `serial write failed forwarding 'STATUS' ... Write timeout` 12:31:08). The faster probe also pins death to a 3 s window, and intersecting the three idle runs leaves **1027-1030 s after the port opened**. Two incidental findings: pressing RESET under a live broker surfaces as `ClearCommError failed (PermissionError(13, 'The device does not recognize the command.', None, 22))` - error **22**, and it reopens cleanly, unlike the fatal error 31 - so that is the board re-enumerating, not a second failure mode; and `clients=0` meant no logger, so the firmware's own `ms` was lost again (fixed by ADR-0064: the broker now logs it itself).
    - **The clock is still ambiguous, and the wall clock cannot settle it.** 2^20 ms = 1048.576 s is ~18 s past the observed window, which is inside the uncertainty of when RESET was pressed plus however long Windows took to notice the re-enumeration. Worse, "time since boot" and "time since the host attached" have been the *same instant* in all five runs, because `setup()` blocks on `while (!SerialUSB) { delay(10); }` before configuring anything - the board does nothing until a host opens the port.
    - **[correction 2026-07-29] The `<ms>,` prefix is the firmware's SESSION clock, not uptime** (`millis() - session.startMs`, set at the end of `setup()` and again on every MODE switch; true `millis()` is never transmitted). So every "uptime" figure above - occurrence 1's 972401 ms included - is time since the session started, which coincided with time-since-attach in those runs; the intervals hold, the label did not. **E1b below is therefore void**: run on the rig at 10:50, after a RESET plus a five-minute wait, it read `firmware session clock at connect: 3986 ms` - the session simply starts when the host attaches, so a pre-connect wait can never appear in it.
    - **E1b (VOID - see the correction above; kept for the record):** press RESET, wait **5 minutes with the broker not running** - `millis()` counts during that wait but `loop()` does not run - then start `python rig_broker.py --port COM4 --probe-quiet 2 --probe-interval 2 --probe-dead 8`. The broker now prints `firmware uptime at connect` (expect ~300000 ms, confirming the wedge) and the board's clock at death. Dying near **ms 1030000** (~12 min after connect) means absolute `millis()`, and the exact value settles the 2^20 question; dying near **ms 1330000** (~17 min after connect) means the clock starts when the host attaches and `loop()` begins, which points at the USB stack rather than a plain counter.
  - [occurrence 6, 2026-07-29, the E1b run - void as a session-clock test, decisive by accident] **2^20 ms of board uptime is dead as a theory.** RESET ~10:45:09, port opened 10:50:11, last line `ms=1030039`, write failed **11:07:21** - 1030.0 s after the open, and the arithmetic closes to the second. But the board crossed uptime 1,048,576 ms at ~11:02:38 and kept answering probes for another 4.7 minutes, dying at an uptime of ~1330 s that matches nothing in any other run. Time since the host opened the port is the only quantity that reproduces.
  - [occurrence 7, 2026-07-29, E3 - "allow the computer to turn off this device" unchecked on the USB 3 hub] **Host-side hub power management is not the cause**, and a lucky 6 s offset made this run doubly informative. Last line `ms=1036321` at 11:52:33, write failed 11:52:35. This was the first run where the firmware session and the port open were separable: a previous broker still retrying grabbed the port when RESET was pressed, so the session began ~11:35:17 while this broker opened 11:35:21-23. Measured from the session it was 1036.3 s; measured from the open, ~1030 s, matching occurrence 6. Note the two remaining power knobs are untouched: the device node's own Power Management tab and the power plan's USB selective suspend setting.
  - [occurrence 8, 2026-07-29, E1c - open, run 2 min, close, wait 5 min, reopen] **The countdown is created by the port open and rearmed by every reopen.** The first broker opened 11:57:11 and was Ctrl-C'd at 11:59:13; the board kept running unattached (session clock **433745 ms** at the 12:04:23 reconnect - 7.2 min, matching the 11:57:09 session start exactly). Death: last line `ms=1462023`, write failed **12:21:33**, which is **1030.3 s after the reopen** and not the ~10 min the first-attach hypothesis required. Three runs, three unrelated firmware clocks at death (1030.0 s, 1036.3 s, 1462.0 s), one constant: ~1030 s since the host opened the port. Two further exclusions: a bug living purely inside the broker process is out, because after a wedge a **fresh** process still cannot open the port until someone presses RESET; and the wedge is not merely a refusal to configure - while the board sat wedged at 12:31 the native port was **absent** from the device tree, with a phantom `Unknown USB Device (Device Descriptor Request Failed)` sitting at the same hub location (`USB\VID_0000&PID_0002\5&30741CDD&0&9`, the location shared by `Arduino Due (COM4)` and the old `Bossa Program Port` node). Windows reports every absent device as "Unknown", so that node cannot be dated with confidence, but it is the signature of a device that stopped answering control transfers - which is exactly what error 31 means to pyserial. Suspects left: the SAM3X's own USB device stack, or the Windows driver instance created by the open.
    - **E6 (2026-07-29): the Programming port does not wedge, so the fault is in the SAM3X's own USB stack.** Same firmware rebuilt with `DUE_USE_NATIVE_USB 0` so `CONSOLE` is `Serial` (UART0 -> ATmega16U2): a different UART, a different chip and different endpoints, but the same `usbser.sys`, hub and cable. Two cheap characterizing tests remain if it ever matters (a direct USB 2 motherboard port, and a second PC), and the incidental confirmation that opening the Programming port resets the board came from the session clock reading 3791 ms at an open that followed a 30 s-old upload.

- #260720_TrackingDelays Rat tracking gets less reliable (more often loses tracking confidence) and/delayed (the determination of when a rat enters a zone is variable; physically the rat could be well into the zone before the determination is made that animal has entered it; this will affect the spatial consistency of when audio cues are presented if a cue is to be triggered when the rat enters a zone) if the blocker is in view and being tracked. This reliability/delay issues also exacerbate if I start video recording and also once the upgrade to the multi-blob based rat tracking was implemented.
  - [investigation 2026-07-21] Not one cause but three: (1) tracker per-frame CPU on the grab thread - blocker+clustering was doing a redundant second detect+cluster pass every frame the tape is visible (worse *even far from the blocker*), dropping source frames -> broken association -> coasting; **reduced** via single-pass containment-drop (ADR-0039) + a `track: avg/peak ms` readout in the Camera tab to watch it. (2) Recording competes for CPU cores (H.264 all-cores) - see FW-0013 (NVENC/core cap). (3) Zone-entry lateness is mostly architectural (poll interval x min_dwell_ticks floor, ADR-0025), not CPU - see FW-0014. Structural root (tracking inline on the grab thread) tracked in FW-0012. Keep open pending on-rig `track_ms`/`src-drop` data.
  - [update 2026-07-22] Structural root (FW-0012) **implemented**: tracking moved off the grab thread onto a newest-frame worker + publisher (ADR-0040). On-rig confirms the decoupling - with the blocker tracked and recording on, per-frame `process()` runs ~3.2->4.4 ms but `src-drop` stays flat while a new `track-skip` counter absorbs the rare worker lag (~0.1% of ~10.5k frames), so tracking cost no longer drops source frames. Remaining facets stay open: recording CPU contention (FW-0013 - deferred, ample headroom at current load) and the architectural zone-entry latency floor (FW-0014). Still pending `maze_state_validate.py` latency/jitter numbers before closing the "delayed zone-entry" facet.
