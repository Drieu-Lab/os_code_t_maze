# Bugs

Quick capture of things that are broken or wrong. One bullet each; rough is fine.
See [`README.md`](README.md) for how these get triaged.

Format: `- #YYMMDD_ShortName <what's wrong> [where, if known]`

Assign a unique `#YYMMDD_ShortName` handle once, date-first (e.g.
`#260710_DoubleReward`). The date prefix is the creation date, so no separate
date column is needed. Don't rename a handle after you've referenced it elsewhere
(commits, `future-work.md`) so those references stay valid.

- #260727_SerialLockout The Due stops talking to the host mid-run while staying enumerated in Device Manager (no error code, nothing in the Windows event log). Manual feed / speaker buttons do nothing, the GUI readouts just stop updating, and restarting the rig fails with `PermissionError(13, 'A device attached to the system is not functioning.', None, 31)`. The Due's RESET button recovers it (no cable replug needed), which points at a hung firmware `loop()` - the SAM3X services its USB CDC endpoints from `loop()`. Twice on 2026-07-27: (1) 29 s into a Phase 3 session with H.264 recording, last line `S,3,1` at 13:43:46 (firmware uptime 16.2 min); (2) on a completely idle board - empty maze, nothing recording, no tones since boot - dead somewhere in the 19-minute window between 14:06:17 and 14:25:35. Correlates with the PROTO v6 reflash (`254c6c5`, 2026-07-23), and Phase 2a on pre-v6 firmware ran 30-60 min repeatedly without it, but the idle case may be an older mode nobody had watched for. Ruled out: pins 4/5 (unwired), USB contention with the camera (it is GigE), host CPU/disk load, USB bus events, dead USB hardware. **Partly addressed:** the host now detects it in ~25 s and logs it instead of silently freezing for 17 minutes (ADR-0062), and the always-on 80 kHz tone interrupt - the leading suspect for the idle case - now runs only while a tone sounds (ADR-0063). Root cause still unconfirmed; keep open until an idle board survives 30+ min on the reflashed firmware. Remaining suspects: the `CONFIRM wired` TONE_ON/TONE_OFF TTL pins 6/7, a latent out-of-bounds write, or a non-firmware change from the same week (an `FTDI FT600 USB 3.0 Bridge Device` shares the Due's USB controller).

- #260720_TrackingDelays Rat tracking gets less reliable (more often loses tracking confidence) and/delayed (the determination of when a rat enters a zone is variable; physically the rat could be well into the zone before the determination is made that animal has entered it; this will affect the spatial consistency of when audio cues are presented if a cue is to be triggered when the rat enters a zone) if the blocker is in view and being tracked. - #260729_SessionTaskFolder A session's `task/` folder was left empty and its manifest's `phase3_task` pointed at the PREVIOUS session's CSV, so Phase 3 kept writing into the old session for minutes after the new one started. Seen on `600_20260727_134317`, whose manifest named `000_20260727_132752\task\phase3_000_20260727_132752.csv`; that file's last write (13:45:27) falls inside session 600's 13:43:17-13:46:32 span. Nothing was lost, but the per-session tree (ADR-0049) was wrong and the manifest lied about where a session's task data lives. Cause: Phase 3 binds its data-file path only in `_arm_session`, which runs on the cue gate's *rising* edge - and ADR-0060 has the operator arm Phase 3 *before* Start Session, so the gate is already open when the session mints its folder and no edge fires. `set_session_context` stored the new id/folder but left the path alone, `_resolve_paths` recorded it unchecked, and nothing cleared the context on Stop, so a re-arm between animals wrote into the already-closed session's folder. **Fixed 2026-07-29, ADR-0066:** Start enqueues a rebind onto the actuation thread (re-points the path + header id, keeping the task, trials and tallies), Stop releases the context, and the manifest refuses any path outside the session tree (`session_log.path_within_session`). Confirmed by an instrumented headless trace of both controllers and locked in by `host/test_session_phase3_wiring.py`. Follow-up left open: a mid-session gate reopen still restarts the plan and overwrites the session's file (FW-0026).
